# SPSC 与 MPMC 吞吐量 O3 性能测试

## 目标

本文档记录 [tests/mpmc_spsc_performance_test.cpp](../tests/mpmc_spsc_performance_test.cpp) 的性能测试结果，目标是回答四个问题：

1. `SPSC` 与 `MPMC` 在读写吞吐量上差多少。
2. 不同 `MPMC` 配置下，吞吐量如何变化。
3. 绑核与不绑核，对 `SPSC` / `MPMC` 吞吐量分别有什么影响。
4. 当 consumer 变复杂时，`SPSC` 和 `MPMC` 的结论是否会改变。

这里比较的是：

- `SPSC 1P1C`：专用单生产者/单消费者环形队列
- `MPMC 1P1C`：用多生产者/多消费者队列去跑 `1P1C`
- `MPMC 2P2C`
- `MPMC 3P3C`
- `MPMC 4P4C`

## 相关文件

- `SPSC` 实现： [include/spsc_ring_buffer.h](../include/spsc_ring_buffer.h)
- `MPMC` 实现： [include/mpmc_ring_buffer.h](../include/mpmc_ring_buffer.h)
- 性能测试： [tests/mpmc_spsc_performance_test.cpp](../tests/mpmc_spsc_performance_test.cpp)
- 构建配置： [CMakeLists.txt](../CMakeLists.txt)

## 构建与运行

在仓库根目录执行：

```bash
cmake -S . -B build
cmake --build build --target mpmc_spsc_performance_test -j
./build/mpmc_spsc_performance_test
```

说明：

- 该目标单独使用 `-O3` 编译。
- 程序内部会分别跑两组：
  - 绑核模式
  - 不绑核模式
- 每组又会分别跑两类 consumer：
  - 轻消费者
  - 复杂消费者
- 绑核时：
  - producer 线程按顺序绑定到 `core 0, 1, 2, ...`
  - consumer 线程继续按顺序绑定到后续核心
  - 当线程数超过在线 CPU 数时，会按 CPU 数取模复用核心

## 参数

- `--ops N`：每轮总消息数，默认 `6000000`
- `--rounds N`：每种配置重复次数，默认 `3`
- `--consumer-work N`：复杂 consumer 每条消息的额外计算轮数，默认 `64`

## 测试环境

- CPU：AMD Ryzen 5 4500U
- 核心 / 线程：6C / 6T
- 操作系统：Linux
- 编译优化：`-O3`
- Ring 容量：`65536`

## 实测结果

说明：

- “轻消费者”结果来自原始轻负载路径。
- 为控制复杂 consumer 的总测试时长，下面复杂 consumer 结果使用：
  - `--ops 1500000`
  - `--rounds 1`
  - `--consumer-work 64`

复杂 consumer 的含义是：

- 每次消费一条消息后，不是简单做一次加和
- 而是执行一段固定轮数的混合整数计算
- 用来模拟“消费端存在真实计算负载”的情况

## 结果分析

### 1. 轻消费者下，`SPSC` 明显快于 `MPMC 1P1C`

在同样都是 `1P1C` 的情况下：

- `SPSC 1P1C`（绑核）：`66.52 Mops`
- `MPMC 1P1C`（绑核）：`49.52 Mops`

`MPMC 1P1C` 只有 `SPSC 1P1C` 的约 `74%`。

原因很直接：

- `SPSC` 是专用算法
  - 不需要 `CAS` 竞争抢位
  - 生产者和消费者各自只写自己的游标
  - 只需要最少量的同步
- `MPMC` 为了支持任意线程数：
  - 每个 `push/pop` 都要做更复杂的 `CAS + sequence` 状态判断
  - 即使在 `1P1C` 场景下，这些通用性开销仍然存在

所以如果业务就是严格 `1P1C`，且 consumer 很轻，优先用 `SPSC` 是合理的。

### 2. 复杂消费者下，结论会发生变化

当 consumer 端有实质计算负载时：

- `SPSC 1P1C` 不再天然最优
- `MPMC 1P1C` 甚至可能比 `SPSC 1P1C` 更快
- `MPMC 3P3C` / `4P4C` 能通过多 consumer 并行把总处理吞吐显著抬高

原因是此时系统瓶颈已经从：

- 队列同步路径

转移到：

- consumer 的真实计算负载

也就是说：

- 如果消费逻辑很轻，队列开销占主导，`SPSC` 更有优势
- 如果消费逻辑很重，计算开销占主导，允许多 consumer 并行的 `MPMC` 可能让系统总吞吐更高

### 3. `MPMC` 的吞吐量不会随线程数线性上升

从轻消费者绑核结果看：

- `MPMC 1P1C`：`49.52 Mops`
- `MPMC 2P2C`：`6.09 Mops`
- `MPMC 3P3C`：`11.22 Mops`
- `MPMC 4P4C`：`10.15 Mops`

这说明多线程数增加后，瓶颈很快转移到：

- `enqueue_pos_` 上的生产者 CAS 竞争
- `dequeue_pos_` 上的消费者 CAS 竞争
- slot `sequence` 的 cache coherence 流量
- 线程数变多后的调度与缓存争用

`MPMC` 的本质是“正确支持并发”，不是“线程越多吞吐越高”。

### 4. 在这台 6C/6T 机器上，`3P3C` 往往是更平衡的点

从结果看：

- 轻消费者绑核：`3P3C` 明显好于 `2P2C`
- 复杂消费者绑核：`3P3C` 达到 `15.84 Mops`，是全部 MPMC 配置里最好的

这说明在当前 6 核 6 线程机器上：

- `3P3C` 正好把 CPU 资源利用得更充分
- `4P4C` 因为总线程数达到 8，已经超过在线 CPU 数，容易进入过度调度区间

### 5. 绑核对轻消费者更敏感，对复杂消费者不总是决定性因素

从轻消费者结果可以看到：

- `SPSC 1P1C`：`2.04x`
- `MPMC 1P1C`：`3.28x`

说明绑核对“以同步开销为主”的场景帮助很大。

但在复杂消费者场景里：

- 主要成本已经有很大一部分变成消费者计算
- 队列同步和迁核开销在总时间中的占比下降

因此不能简单说“绑核一定让复杂 consumer 场景更快”，只能说：

- 如果目标是稳定、可重复地观察队列本身差异，绑核仍然很有意义
- 如果目标是看整体系统吞吐，多 consumer 并行能力往往更关键

## 结论

在当前机器和 O3 条件下：

1. **如果 consumer 很轻，严格 `1P1C` 场景优先使用 `SPSC`**
   - 吞吐明显高于把 `MPMC` 当作 `1P1C` 使用

2. **如果 consumer 很重，不能只看单条队列开销**
   - 多 consumer 并行可能让 `MPMC` 的系统总吞吐反超 `SPSC`

3. **`MPMC` 的价值不仅在于通用并发支持，也在于复杂处理下的并行扩展能力**
   - 虽然有 CAS 和 coherence 成本，但在复杂 consumer 场景里，并行化收益可能超过这些同步开销

4. **绑核是一个很有效的优化手段，尤其对轻消费者和低线程数配置更明显**
   - 对轻消费者场景，绑核能显著减少迁核、缓存抖动和调度噪声

5. **`MPMC` 的最佳配置依赖机器拓扑、线程数以及 consumer 负载**
   - 在这台 6C/6T 机器上，`3P3C` 通常比 `2P2C` 和 `4P4C` 更平衡

## 建议的后续实验

- 增加更多 `MPMC` 配置，例如 `5P5C`、`6P6C`
- 固定 producer 和 consumer 到不同核心簇的机器上测试

  - `cache-misses`
  - `LLC-load-misses`
  - `context-switches`
  - `cpu-migrations`
- 将 `MPMC` 与 `MSQueue`、`MutexQueue` 一起纳入同一组绑核 / 不绑核对比
